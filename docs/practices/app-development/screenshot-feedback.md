# 截屏后的轻量反馈入口

适用于希望在用户截屏后提供问题反馈入口的原生 iOS App。来源是 2026-10-24 云乐坊的交互设计与实现检查；系统 API 事实引用 Apple 文档，项目选项不作为其他 App 的默认规范。

## 截屏不是提交反馈

用户也可能只是保存或分享内容。收到截屏事件后，在 App 内提供可关闭、自动消失的小按钮；不直接打开反馈表单，不遮挡主要操作，不抢走输入焦点。用户点击后才进入已有反馈流程，日志或附件沿用该流程的选择与确认。

`UIApplication.userDidTakeScreenshotNotification` 在截屏完成后发出，且没有 `userInfo`，不能从通知中取得截图文件。若以后需要用户刚截取的原图，应让用户主动选择并预览确认；重新渲染 App 页面不能替代那张系统截图。[Apple 截屏通知文档][screenshot]

将入口做成独立的持久设置。云乐坊选择默认开启、短暂显示、允许在设置关闭，第一版不做图片附件；这些是该项目的产品选择。能否默认开启及显示多久，应结合内容类型、截屏频率和遮挡情况决定。

## 为提示定义完整的生命周期

实现前至少明确以下行为：

- 连续截屏合并为一个提示，避免叠加或反复抢占视线。
- 用户主动关闭后，在本次使用期间抑制再次出现；与自动超时消失区别处理。
- 设置关闭立即撤掉提示，取消待展示状态和计时任务；打开反馈页时不再提示反馈入口。
- 只在所属场景前台可交互时展示和计时，避免用户返回 App 时按钮已经在后台过期。离开场景后，明确选择保留剩余时长还是丢弃过期提示，避免很久后突然出现。
- 辅助功能焦点停留在提示的按钮或关闭控件上时，暂停自动消失的倒计时，给用户完成操作的时间；提示出现时不主动抢焦点或播报。

SwiftUI 的 `scenePhase` 从 View 读取时反映所在场景，从 App 读取时是多个场景的聚合状态；多窗口 App 不能仅凭“有一个场景活跃”就给所有窗口显示提示。[Apple ScenePhase 文档][scene]

系统截图预览出现与退出的通知时序需要在目标 iOS 版本实测。不要假设它始终造成相同的 inactive/background 切换，也不要用固定延迟充当“用户已经回到 App”的证据。

## 全局入口要检查实际展示层级

云乐坊的云应用由 UIKit 导航控制器以全屏方式呈现，独立于主界面的 SwiftUI 内容树。[项目呈现代码][presentation]

只在 SwiftUI 根视图增加 `overlay`，不能据此认定入口也会覆盖后来呈现的 UIKit 全屏页面。检查普通页面、已有 sheet、全屏云应用和反馈页分别由谁承载；将入口挂在能覆盖目标页面的层级。把提示挂到窗口层时，应绑定正确的 scene，让按钮之外的触摸继续传给下层，并保留已有 key window 与输入焦点。

快捷入口也要复用原有的登录与返回反馈流程。认证可能重置或销毁原先呈现反馈页的控制器，应由生命周期稳定的根级对象持有草稿和登录续接状态；验证登录成功后恢复，也验证取消登录后草稿仍可恢复。

云乐坊的一次视觉复验发现，状态测试虽已通过，底部胶囊却出现在顶部：当时 `UIWindow.keyboardLayoutGuide` 高度为零，纵向位置没有按预期约束，而测试只断言它在窗口内。窗口层覆盖物应核对当前呈现控制器内容视图的 `keyboardLayoutGuide` 与坐标系，并随控制器切换更新锚点；验收直接断言预期的底部位置和间距。这里记录的是该项目观察到的问题，不推断所有窗口层 guide 都有相同行为。

## 分开记录状态测试、视觉检查与真实截屏

| 验证方式                   | 能证明什么                                     | 不能据此声称什么                                 |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------ |
| 单元测试或主动发送截屏通知 | 去重、开关、计时、会话抑制及反馈路由的状态行为 | 系统截屏时通知真实到达、系统预览退出后的时序正确 |
| 自动化截取页面图像         | 当时的布局、遮挡、按钮视觉效果                 | 这次取图一定触发了 iOS 的用户截屏通知            |
| 真机使用系统截屏操作       | 目标系统版本的事件、预览返回和交互结果         | 其他系统版本、其他呈现层级也已验证               |

测试代码直接调用关闭处理器，只能记为关闭逻辑验证；实际按钮的命中与事件绑定仍需 UI 验证，不能写成已点击界面上的「完成」。

真实截屏验收至少覆盖正常保存/分享、连续截屏、进入系统预览后返回、手动关闭、设置关闭，以及全屏页面中点击后进入反馈页。报告说明设备、系统版本和已覆盖路径；未进行的真机检查保留为待验，不能用注入事件或自动化截图代替。
